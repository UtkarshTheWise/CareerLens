Frontend, what to rely on:
- `matchJob`: uses the profile's latest finished analysis, no GitHub call. 409 `no_analysis` if there is none. A posting with `source: "llm"` or no `required_skills` is read by the model first (page text only, PII stripped); if the model is down the catalogue is scanned against the description instead and `summary` says so. `keyword_match` = matched ÷ required, `evidence_match` = Σ credit(level) ÷ required, both 0-100; with nothing required the `nice_to_have` list is the denominator; with neither, both are 0 and `summary` says the posting lists no recognisable skills. Skills outside the catalogue are not counted but named in `summary`. `normalized_posting` uses catalogue display names, with `company`, `location` and `deadline` filled when the page lacked them.
- Applications: `status` defaults to `saved`; moving to `applied` stamps `applied_at` (unless you send one). `PATCH` changes only the fields you send; `deadline` and `notes` can be cleared with `null`. Another user's application is 404.
- Cohorts: `insights` and `students` take any `role_id`; a student whose latest analysis is for another role is re-scored from the stored signals (no LLM), so the role switch on the dashboard always works. Students without a finished analysis count in `student_count` but not in `analysed_count` and are absent from `students`. `students` is sorted weakest first. `understanding` is always present in insights (zeros until quizzes exist, and `by_skill` is empty then). Unverified rate is only listed for skills claimed by at least 2 students. Export is `text/csv`, one row per student (profile_id, name, github_username, department, score, band, coverage, top_gap, at_risk, understanding; no email); cells starting with `= + - @` get a leading `'`.
